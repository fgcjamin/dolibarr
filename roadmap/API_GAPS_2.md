# API_GAPS — backlog des manques dans le serveur MCP `dolibarr-accountancy`

Ce fichier liste ce qui a manqué, côté outillage (serveur MCP `mcp__dolibarr-accountancy__*`), pour effectuer le travail comptable directement depuis Claude Code. À faire remonter à qui maintient ce serveur MCP (voir le repo `fgcjamin/dolibarr` / config `.mcp.json`). Mettre à jour au fil des séances plutôt que de redécouvrir les mêmes limites.

## 1. Pas d'écriture comptable manuelle libre
`accounting_ledger` n'expose que `list, get, update, delete, balance` — aucune opération `create`. Toute écriture au grand livre doit passer par `accounting_journal_transfer` (transfer) sur un document source déjà existant (facture liée, ligne bancaire, note de frais...).
**Impact** : impossible de saisir les écritures d'ouverture (à-nouveaux) 2024, ou toute écriture OD manuelle (ex : ajustement de fin d'exercice, écriture de régularisation), sans passer par l'UI Dolibarr.
**Souhaité** : une opération `create` sur `accounting_ledger`, ou une opération dédiée type `accounting_manual_entry` acceptant une liste de lignes (compte, libellé, débit/crédit) formant une pièce équilibrée, avec le même contrôle d'équilibre que fait Dolibarr côté UI.
**Résolu (2026-09-02, Phase 12, `roadmap/backlog.md`)** : nouvel endpoint `POST ledger` dans `api_accountancy.class.php` (méthode `postLedgerEntry()`). Prend `code_journal`, `doc_date`, `doc_ref`, `lines[]` (compte, libellés, débit/crédit) ; rejette une pièce non équilibrée (somme débit ≠ somme crédit), une ligne sans compte, ou une ligne avec débit et crédit tous deux non nuls — mêmes contrôles que le formulaire UI (`accountancy/bookkeeping/card.php`). À faire remonter au serveur MCP : ajouter une opération `create` sur `accounting_ledger` qui appelle ce nouvel endpoint.

## 2. Pas moyen de modifier `accountancycode` sur une ligne bancaire existante
`bank_transactions` expose `accountancycode` uniquement sur `create_line`. Aucune opération `update_line`.
**Contournement utilisé** : transférer la ligne au journal BQ (elle atterrit automatiquement sur le compte 471 "comptes d'attente" en contrepartie de 512), puis utiliser `accounting_ledger update` pour reclasser l'écriture 471 vers le bon compte. Fonctionne mais demande 2 appels (transfer global + update par ligne) au lieu d'un seul, et pollue transitoirement le compte 471.
**Souhaité** : `bank_transactions` → opération `update_line` acceptant au moins `accountancycode`.
**Confirmé, backlogué (2026-09-02, Phase 13 "not started", `roadmap/backlog.md`)** : gap réel côté Dolibarr, pas seulement côté MCP. `AccountLine` (`htdocs/compta/bank/class/account.class.php`) n'a **aucune** méthode `updateAccountancyCode()`, même non exposée — `updateLine()` de l'API (`api_bankaccounts.class.php:680`) ne touche que `label`. Nécessite d'ajouter la méthode modèle puis de la brancher sur l'API. Reporté à une session future (fichiers Dolibarr stock, hors additions propres à ce fork, périmètre plus large que la Phase 12).

## 3. `limit` ignoré par `bank_transactions list_lines`
Un appel avec `limit: 1` a quand même renvoyé les 502 lignes du compte (payload > 400k caractères, bascule systématique en fichier).
**Souhaité** : que `limit`/`page` soient effectivement appliqués côté serveur, ou au moins documentés comme non supportés pour cette opération si c'est un choix délibéré.
**Confirmé, backlogué (2026-09-02, Phase 13 "not started", `roadmap/backlog.md`)** : bug réel confirmé. `getLines()` (`api_bankaccounts.class.php:461`) ne prend aucun paramètre `limit`/`page`, ne construit aucun `LIMIT`/`OFFSET` SQL, et renvoie systématiquement toutes les lignes — une référence `$limit` commentée et jamais branchée (ligne 493) suggère une pagination commencée puis abandonnée. Reporté avec l'item #2 (même fichier, même session future).

## 4. `sqlfilters` : syntaxe limitée
- `IN (...)` non supporté : `(t.account_number:in:('218105','218106',...))` → `400 Bad Request`.
- Combinaisons `AND`/`OR` imbriquées avec parenthèses multiples testées sans succès pour filtrer sur plusieurs champs à la fois.
**Contournement** : récupérer la liste complète (avec `properties` réduit) et filtrer côté client (jq/Python).
**Souhaité** : support de `IN`, ou au minimum un exemple de syntaxe valide pour des filtres combinés dans la description de l'outil.
**Pas un gap côté Dolibarr (2026-09-02)** : `IN`/`NOT IN` sont déjà supportés par `forgeSQLFromUniversalSearchCriteria()` (`htdocs/core/lib/functions.lib.php:15724`), de même que les groupes `AND`/`OR` imbriqués sur des champs différents (couvert par `test/phpunit/FunctionsLibTest.php:190-192`). La syntaxe testée dans l'exemple ci-dessus est invalide : la grammaire n'accepte **pas** de parenthèses supplémentaires autour de la liste de valeurs (`[^\(\)]+` dans la regex de l'opérande) — la forme correcte est `(t.account_number:in:'218105','218106')` (sans parenthèses autour de la liste elle-même), voir `FunctionsLibTest.php:266-274`. À faire remonter au serveur MCP : corriger l'exemple de syntaxe dans la description de l'outil, rien à changer côté Dolibarr.

## 5. Pas de moyen de lister les taux de TVA (VAT rate ids)
`accounting_vat_tax_accounts` n'a que `put_vat_rate` (exige un `id` de taux de TVA), `list_chargesociales`, `put_chargesociale`. Aucune opération pour lister les taux de TVA et récupérer leurs ids.
**Impact** : impossible de configurer `ACCOUNTING_VAT_SOLD_ACCOUNT` / `ACCOUNTING_VAT_BUY_ACCOUNT` / `ACCOUNTING_VAT_PAY_ACCOUNT` proprement par taux sans deviner les ids ou passer par l'UI.
**Souhaité** : une opération `list_vat_rates` (ou équivalent) sur cet outil, ou sur un outil dédié aux taux/dictionnaires Dolibarr.
**Résolu (2026-09-02, Phase 12, `roadmap/backlog.md`)** : gap réel confirmé (précision : le besoin réel était de récupérer les ids de taux de TVA pour *définir* `accountancy_code_sell`/`accountancy_code_buy` par taux via `put_vat_rate`, pas pour les globals `ACCOUNTING_VAT_*_ACCOUNT` qui attendent un code compte, pas un id). `PUT vatrates/{id}/accountingcodes` existait déjà (c'est `put_vat_rate`), et `chargesociales` avait déjà sa paire GET+PUT symétrique — seul le GET manquait côté taux de TVA sur cette même surface d'API, obligeant à passer par l'endpoint générique sans rapport `GET dictionary/vat`. Nouvel endpoint `GET vatrates/accountingcodes` dans `api_accountingsetup.class.php` (méthode `getVatRatesAccountingCodes()`), miroir de `getChargesocialesAccountingCodes()`. À faire remonter au serveur MCP : ajouter une opération `list_vat_rates` sur `accounting_vat_tax_accounts` qui appelle ce nouvel endpoint.

## 6. Filtrage par date sur `accounting_ledger` (list/balance) pas fiable à 100 %
Un appel `list` avec `date_start`/`date_end` a renvoyé `[]` alors que des écritures existaient bien dans l'intervalle (confirmé ensuite via un `list` filtré par `code_journal` sans date). Pas eu le temps de bien caractériser le bug (champ de date utilisé côté serveur ? `doc_date` vs autre chose ?).
**Souhaité** : investiguer/documenter précisément quel champ de date ces filtres utilisent réellement côté Dolibarr, pour savoir quand s'y fier.
**Pas un gap trouvé (2026-09-02)** : audit de `_buildLedgerFilter()` (`api_accountancy.class.php:941`) et des trois méthodes `BookKeeping::fetchAll()`/`fetchAllByAccount()`/`fetchAllBalance()` — le filtre utilise systématiquement `t.doc_date` (colonne `DATE` simple, pas de partie horaire, donc pas de piège d'arrondi `strtotime()`), avec le même alias `t` que dans le `FROM`. Aucun bug d'alias ou de mauvaise colonne trouvé ; le filtrage est cohérent entre les trois méthodes. Sans repro exploitable (jeu de données exact, requête exacte), impossible d'aller plus loin — à rouvrir si un cas reproductible est isolé (ex : capturer la requête SQL exacte envoyée et les dates exactes en jeu).

## 7. Pas d'outil générique factures/tiers
Le serveur MCP exposé ici (`dolibarr-accountancy`) ne couvre que la comptabilité — pas de `mcp__dolibarr__*` générique pour lister/créer des factures clients/fournisseurs, des tiers, etc. (cohérent avec le nom du serveur, mais à noter : sans ça, impossible de vérifier ou saisir les factures pour ventiler les remises CB avec le détail HT/TVA).
**Souhaité** : si la saisie de factures depuis Claude Code est un besoin réel pour ce projet, prévoir un serveur MCP complémentaire (ou étendre celui-ci) couvrant `/invoices`, `/supplier_invoices`, `/thirdparties`.
**Contournement trouvé le 2026-09-02** : l'API REST native de Dolibarr expose déjà tout ça (`POST /thirdparties`, `POST /supplierinvoices`, `POST /supplierinvoices/{id}/lines`, `POST /supplierinvoices/{id}/validate`), accessible directement avec `DOLAPIKEY` (`dolibarr-deployment/.env`) sans passer par le MCP. Utilisé pour saisir 228 factures fournisseurs 2024 en une séance. Le fork custom (`fgcjamin/dolibarr`) expose aussi `/accountingbind/supplierlines/{lineid}/bind` (et sa version en masse `/accountingbind/supplierlines/bind`) pour assigner le compte comptable à une ligne de facture (`fk_code_ventilation`) — c'est probablement ce qu'utilise en interne le serveur MCP `dolibarr-accountancy` pour la ventilation, ce qui suggère qu'étendre ce même serveur MCP avec des outils `create_thirdparty`/`create_supplier_invoice`/`bind_supplier_line` serait cohérent avec son architecture actuelle plutôt que de créer un serveur séparé. Détail complet (noms de champs exacts, pièges silencieux comme `subprice`/`desc` ignorés sans erreur) dans `memory/LEARNINGS.md`.
**Pas un gap côté Dolibarr (2026-09-02)** : confirmé — l'API REST native (`/thirdparties`, `/supplierinvoices`, `/accountingbind/supplierlines/...`) couvre déjà ce besoin, comme le contournement documenté ci-dessus le montre. Rien à changer côté Dolibarr ; l'extension éventuelle du serveur MCP avec des outils `create_thirdparty`/`create_supplier_invoice`/`bind_supplier_line` reste une décision côté MCP, pas ce dépôt.
